# Entitlement Certification Service with Segregation-of-Duties Detection

A C#/.NET 8 entitlement certification service over a simulated investment-operations
application: permissions are modeled as roles plus attributes (an RBAC+ABAC hybrid,
where a role's baseline permissions only apply within the business unit and
instrument class scope on the grant), reviewed through quarterly access-review
campaigns. A fast, indexed detector flags segregation-of-duties conflicts (the named
case: a single user able to both create and approve a trade instruction) and
orphaned grants (a grant left active for a terminated user or a deleted role), diffed
exactly against a deliberately naive brute-force reference oracle. The reviewer
evidence pack is a pure function of an append-only grant log and regenerates
byte-identically on every call. Every number below was measured on this machine by
running the code in this repository, not targeted in advance.

## Why this exists

This is a small version of the access-certification layer inside an asset manager's
identity and entitlements program: the part that periodically reviews who can do
what, catches the control failures a maker-checker policy exists to prevent, and
hands a reviewer a defensible, reproducible evidence pack instead of a spreadsheet
someone eyeballed. It is not an Active Directory or identity-governance product; it
is a rules-based detector over a synthetic entitlement world, built to the same
standard (reference-oracle diff, byte-identity proof, honest false-positive
measurement) as the other C#/.NET services in this portfolio.

## Honest framing

- **A simulated investment-operations application, not a real MFS or any real
  firm's system.** Every user, role, grant, business unit and instrument class in
  this repository is synthetic, generated by `SyntheticPopulationGenerator.Generate(seed: 42)`.
  No real entitlement data, real employee, or real firm's access model appears
  anywhere in this repository.
- **SQLite exercised, SQL Server referenced.** `Entitlement.Api` references
  `Microsoft.EntityFrameworkCore.SqlServer` and `appsettings.json` carries a real
  `SqlServerConnection` string; `Program.cs` switches providers on
  `Database:Provider`. No SQL Server instance was reachable on the machine this was
  built on (no `sqlcmd`, no local service, and Docker Desktop's engine was not
  running either), so every test and every number in this README ran against
  SQLite (`Data Source=entitlement_certification.db`), which is what
  `Database:Provider` defaults to. The SQL Server code path is real, compiled
  configuration, never exercised here. This is the same situation, and the same
  disclosure pattern, as `transaction-monitoring-alert-triage` (see Sibling
  comparison below).
- **The detection and evidence-pack logic never touches a database.** All of
  `Entitlement.Domain` (the append-only log, the snapshot replay, both detectors,
  the evidence pack generator) is plain C# over in-memory data structures. EF Core
  and SQLite/SQL Server exist only in `Entitlement.Api`, to demonstrate the
  persistence path over real HTTP; the measured numbers below come from
  `Entitlement.Tooling` running the Domain code directly, the same separation
  `transaction-monitoring-alert-triage` uses between its Tooling and its Api.
- **No UI.** This is a backend service; the API is a thin ASP.NET Core minimal-API
  surface over the same domain engine, exercised by `WebApplicationFactory<Program>`
  in-process, never a real listening server.
- **Machine and toolchain.** 16 logical cores, Windows 11 (OS version 10.0.26200),
  native Windows, no WSL2 or GPU involved. .NET SDK 8.0.424, runtime 8.0.30, target
  framework `net8.0`, Debug configuration for the measurement run and for
  `dotnet test`. EF Core 8.0.10 (SQLite and SQL Server providers referenced, SQLite
  exercised). xUnit 2.5.3.

### Design deep-dives

**A conflict is scoped, not just a permission pair.** `FastConflictDetector` groups
active grants by `(UserId, BusinessUnit, InstrumentClass)` before checking any SoD
rule. A user who can create equity trade instructions for Equities and separately
approve bond trade instructions for Fixed Income is not flagged: no single scope
grants them both sides of one maker-checker control. This is the ABAC half of the
hybrid model earning its keep; without the scope, the detector would be a plain
RBAC permission-set check and the "roles plus attributes" claim would be decorative.

**The reference oracle shares no code with the fast path.** `ReferenceOracleDetector`
re-derives every scope's permission set from scratch with nested loops and
`Enumerable.Any` linear scans, independently of `FastConflictDetector`'s dictionary
index. The two detectors were written from the same rule catalog but with no shared
helper method, so a bug in one's indexing logic cannot silently reproduce itself in
the other.

**The synthetic population's hardest problem is proving the noise is actually
clean.** `SyntheticPopulationGenerator` seeds exactly 28 defects, then has to fill
the remaining ~3,952 grants without accidentally creating a 29th. Before placing
any noise grant, `WouldIntroduceUnintendedConflict` simulates the merge against that
user's running per-scope permission set and rejects (and retries) any candidate that
would newly satisfy a rule outside a scope the plan deliberately seeded. Getting
this wrong would silently turn "0 false positives" into a property of the generator
rather than the detector.

**The evidence pack has no wall clock in it.** `EvidencePackGenerator.Generate`
takes only the grant log and a quarter label; every number in its output (active
grants, active users, findings, sorted finding ids) is a deterministic function of
the log's own contents. There is no `DateTime.UtcNow`, no GUID, and no
unsorted dictionary enumeration in the output path, which is what makes two
independent calls produce byte-identical text.

**The certification guard is enforced once, in the domain.** `CertificationGuard.ValidateAttempt`
is called by both `CertificationService` (used by the API) and directly by any
future in-process caller; a blank reviewer, a blank reason, or a second attempt at
an already-certified finding are all rejected with the same rule, mirroring
`transaction-monitoring-alert-triage`'s disposition guard.

## Validation

Four independent layers, all exercised on this machine:

1. **Reference-oracle diff.** Small hand-built scenarios in
   `ReferenceOracleAgreementTests` (the named trade-instruction conflict, a mixed
   clean-and-orphan case) plus a full diff over the entire 4,000-grant synthetic
   population, both in the test suite and in the tooling measurement run.
2. **Seeded defect catch rate.** 28 hand-engineered defects (12 SOD-01, 5 SOD-02,
   3 SOD-03, 4 orphaned grants for terminated users, 4 orphaned grants for deleted
   roles), checked by exact finding-id set equality against what the detector
   actually raises, not just a count match.
3. **Evidence pack byte-identity.** Two independent calls to
   `EvidencePackGenerator.Generate` over the same log, hashed with SHA-256 and
   compared, both in `EvidencePackGeneratorTests` and over HTTP in
   `ApiIntegrationTests`.
4. **Append-only invariant.** `AppendOnlyGrantLog.PriorEntriesDigest` hashes the
   first N entries before and after a new append and asserts the digest is
   unchanged, proving the log is genuinely append-only rather than merely "not
   observed to mutate yet".

## Findings: what broke

Nothing broke during this build. The reference-oracle diff agreed with the fast
detector on the first run, over both the hand-built scenarios and the full
4,000-grant population, and the synthetic population generator hit its exact
targets (4,000 grants, 28 seeded defects, 0 unintended conflicts) on the first
genuine attempt. The honest account is that the hard part of this project was
designing the noise-safety check in `SyntheticPopulationGenerator` before running
anything, not debugging it afterward: `WouldIntroduceUnintendedConflict` was
written to simulate the exact same scope-merge logic the detectors use, specifically
so that a false positive, if one occurred, would be a generator bug caught
immediately by `Generate_FastDetectorCatchesAllSeededDefectsWithZeroFalsePositives`
and the tooling run's exact finding-id-set comparison, rather than a quiet
discrepancy. None of the three attempts budgeted for the numeric claims were
needed; all were met on the first run, and that is reported honestly rather than
padded with a manufactured difficulty.

The one number that matters most here is the 28 of 28 seeded-defect catch rate at 0

the known seed list, not by count alone, and both the fast detector and the
independently-written reference oracle agree on the same 28 findings.

## Building and running

Requires .NET 8 SDK.

```
# Build everything
dotnet build

# Run the full xUnit suite (41 tests)
dotnet test

# Regenerate the measurement report (writes docs/measurement_output.txt)
dotnet run --project src/Entitlement.Tooling -- docs

# Run the API locally (SQLite by default; creates entitlement_certification.db next to the binary)
dotnet run --project src/Entitlement.Api
```

To exercise the SQL Server code path instead of SQLite, set
`Database:Provider=SqlServer` against a real SQL Server instance reachable at the
connection string in `appsettings.json`; this was not exercised in this build for
the reason stated in Honest framing above.

## Sibling comparison

`transaction-monitoring-alert-triage` (https://github.com/Manas103/transaction-monitoring-alert-triage)
is the closest repository in this portfolio: C#, .NET 8, ASP.NET Core, EF Core with
the identical SQLite-exercised/SQL-Server-referenced disclosure, and xUnit. Both
projects share the reference-oracle-diffed-against-a-fast-path validation shape and
both separate a Tooling measurement program from a thin API demo surface. The
domain problem is different in a way that changes the detector's shape: the AML
repo screens a stream of transactions against 12 independent, stateless typology
rules per transaction, so its oracle needed only re-derive three of those rules with
a slower windowed scan (60 of 60 seeded typologies caught, review rate 3.139%
against a 4% target, reported honestly as not met). This repository's conflicts are
not per-record at all; they only exist across a user's accumulated grants within one
attribute scope, so the interesting correctness risk is in the grouping key, not in
any single rule, which is why `FastConflictDetector` and `ReferenceOracleDetector`
are diffed over the entire population rather than a transaction-scale sample.

## Limitations

- The synthetic population's noise-safety check (`WouldIntroduceUnintendedConflict`)
  only protects against the three catalog rules; adding a fourth SoD rule later
  would need the same check extended, not just the rule catalog.
- `ReferenceOracleDetector` is O(users x scopes x grants) and takes about 1.2
  seconds over the full 4,000-grant population; it is intentionally never the path
  a real quarterly campaign would run, only the correctness check against the fast
  path.
- There is no authentication or authorization on the API endpoints; `/api/certifications`
  trusts the caller-supplied reviewer identifier, which a real certification
  workflow would tie to an authenticated session.
- The SQL Server EF Core provider is referenced and configured but was never
  exercised against a real SQL Server instance in this build; every measured number
  here ran against SQLite.
- `CertificationService` is in-memory and process-lifetime only; certification
  decisions are not persisted to the EF Core store in this build.
